# The fidelity method

How `npm run fidelity` pairs the design with the build. Its screenshots are in `docs/fidelity/`.

## Phase 1

`scripts/fidelity.ts` opens the design and the local build in Chromium and shoots them side by side, section by section.

- **The design's libraries** are React 18.3.1, ReactDOM 18.3.1 and `@babel/standalone` 7.29.0. The design fetches them from unpkg; the run answers those requests with the same versions from `node_modules`. React 18.3.1 stays at the repository root for this reason, whatever version an app uses.
- **Fonts.** The design loads its fonts from Google, and the build self-hosts the same families (`packages/brand/fonts.css`). Both wait for `document.fonts.ready`.
- **Video** is blocked on both sides, so both show the poster.
- **Fixed bars** are hidden while the sections are shot, then shot on their own.

Any difference in type, spacing, colour or order is a defect. The prices are not: they are the price book's, which the local build shows as it was on 22 September 2026, where v2 says ₹25,000, ₹1,500 and ₹17,000 (ADR 0022, item 39), and they are written "Rs. 30,000" where v2 writes its sign, as the owner ruled on 27 September 2026 (ADR 0025, item 51). Nor are the try-on's consent screen and gate outside production: they show the notices that keep a client's try-on, whose placeholder words await counsel and are longer than v2's (ADR 0084; ADR 0025, item 65). Production's build shows v2's words.

## Phase 2 boards

The Phase 2 files in `design/phase2` run on the same prototype runtime. `test/node/phase2-inputs.test.ts` checks that their `support.js` is byte-identical to `design/support.js`, so the same library routing renders them. Pairs for the client, technician and ops apps follow the Phase 1 method, with two differences:

- **Compare frames, not boards.** A spec board draws several states side by side, with captions and notes around them. Crop the design to the one frame a screen matches, such as `A2 · Code · after 30 seconds`, and shoot the build in that state (a `?state=` preview, as the Phase 1 site has).
- **Match the frame's width:**
  - the client and technician apps at 390 px, the width of the phone frames;
  - the ops console at 1440 px, scaled to the 1000 px the board shows it at.

The board's own furniture is not part of the product: the canvas (`#CFCABE`), captions and notes. The Prototype is a reference for flow and timers only, and a spec board overrules it (`design/phase2/README.md`).

## The client app (P2-F1 and P2-F2)

`npm run build:app -- --env local && npm run fidelity:app` writes `docs/fidelity/client-app/`: board A1 to A3, B1, B2, B3's three states, C1 to C4, C5's first fit and credit, C6's three states, C7's two and C8's first, C9, D1, D2, D3's empty, loading and download states, E1, E2, E3's empty and unavailable states, F1, F2, F4, F5, F6's three states, G1 and G2.

- **The app's API is answered with the design's own example,** Rohit Malhotra with a consultation on Sat 21 Sep, or, fitted, his next service visit on Thu 19 Sep with Imran. No mm-api runs. The login's timers run on Playwright's clock, so A2 is shot 30 seconds after the code was sent, as it is drawn. The payments are shot with the clock in 2027, the year the design dates them in.
- **Fixtures are the API's own shapes.** The C7 and C8 answers are typed as the app's generated `MoveTerms` and `CancelTerms`, so a fixture cannot leave out a field the API always sends. The pay step's clock is held at the moment the hold was made, so its countdown reads the board's 9:42 on every run.
- **The design's photographs are ink blocks with the angle written on them.** The app's are answered with blocks of the same inks (D2's two sides differ, as drawn), and carry no captions.
- **The status bar the phone frames draw is cropped off,** and the app is shot 44 px shorter to match. A2 and A3 draw their back arrow in that band, so both keep it and are shot at the full 844 px.
- **B3, C5, D3, E3 and G2 are not phone screens.** B3, D3 and E3 draw small frames, each with a caption, and G2 the account's three cards on their own. Each is set beside the app's whole screen in that state, or its cards. C5 draws two of the pay sheet's cards on their own, so each is set beside the built sheet alone, without the dark ground above it.

## The referral landing (P2-F3)

`npm run build:site -- --env local && npm run fidelity:refer` writes `docs/fidelity/referral/`: the Landing boards C1 to C4 at 390 px, and C5 at 1440.

- **The page's API is answered with the design's own example:** Rohit's invite, Sector 65 for 122018 and Bandra for 400050. No mm-api runs, and Turnstile is never reached.
- **The page's clock is Friday 20 September 2030 in India,** the eve of the boards' Saturday 21 September, so the date strip starts on the board's day and a booking is confirmed for it on every run.
- **Every `/r/:code` is the one built page** (ADR 0027). The static server maps them as `run_worker_first` does behind Cloudflare, and `?state=` opens each state, as it does for the booking form.
- **C4 draws four small frames.** Each confirmation is set beside the page's whole screen in that state: `c4-booked`, `c4-expired` (`?state=expired`, a booking whose invite had lapsed for this friend) and `c4-on-the-list`. "Pincode not recognised" is the pincode block's own error line, and has no pair.
- **`/book` is the same page without the invite:** no "sent you this", no card, and its own headline and intro. No board draws it. It books with an invite the browser remembered from an earlier `/r/:code`, and its confirmation then carries C4's lines for the invite, as the landing's does (ADR 0089; ADR 0025, item 72).

## The ops console (P2-F3)

`npm run build:ops -- --env local && npm run fidelity:ops` writes `docs/fidelity/ops/`: boards A1, A2, A3, B1, B2 in both its states, B3, C1, C2, C3, D1 in both its cards, D2 and D3.

- **A1 and B1 are the console whole,** as the board draws them: shot at 1440 and brought down to the 1000 px the board shows them at, so both sides are scaled alike. Every other board is a panel within the console, 660 and 484 px wide, drawn at its own size, so those pairs are a panel beside a panel and neither side is scaled.
- **A2 and A3 are reached as ops reach them,** by opening a block and moving it. Nothing is written: the panel sends only on "Move and notify", and the pair is shot before it.
- **B2 draws its two states one above the other,** locked and open, and the console shows one at a time, so each is paired with its own half of the frame.
- **D1 draws two cards,** the day's money over the charges and the disputed charge beside it. The first is built and paired with its own frame. Nothing records a dispute and no client can raise one, so the second is paired with the built queue, the card that holds the evidence and the ruling.
- **The console's API is answered with the board's own figures,** so both sides show the same things. No mm-api runs. The clock is set to 2027, the year the board's waiting dates fall in, so they read without a year, as the board writes them; B2's is set to India's 10:42, the time it letters on the opened photographs. A1 to A3 are shot in 2025, the year whose September falls Fri 19 to Thu 25 as the board's day heads write it, and two days before that week, so the visit A2 moves is more than 24 hours off. The dispatch week is the one the browser tests use (`e2e/ops/fixtures.ts`), written once and read by both, as D2's tasks are: their due dates are written against that day in 2027, so "2 days" and "Overdue 3" read the same on every run.
- **The design's photographs are ink blocks with the angle written on them,** as the client app's boards draw them. The console's are answered with blocks of the same ink, and carry no captions.
- **Nobody in the fixtures is real.** The names, numbers, pincodes and photographs are the board's own or synthetic.

The console's own frame is paired twice: with board A1, which draws it around the dispatch board, and with board B1, which draws it around a client's page. Its column carries the seven sections of the design's eight that the backend has routes for, and then three the design does not draw at all (below). Its third is drawn as "Payments" and built as "No-shows": the section now carries board D1 whole, the day's money over the queue, and the name is left as it was until the owner rules on the console's own navigation. The console opens on Dispatch, as the design does.

**Three sections have no board: Grievances, Deletion requests and Number changes.** They are not a reading of a frame the designer drew, because there is no frame. They exist because the P2-M6 proof of 23 September 2026 found every DPDP action ops are asked to take to be an API call — while the alert ops receive says "answer it in the ops console" and the runbook says a deletion request "waits in ops' deletion requests" (`docs/open-points.md`, item 134). The front-end prompt asks for the number-change and deletion queues "in the same table style", and for an ADR, which is ADR 0078; grievances are ours.

So there is no pair to shoot for them, and `npm run fidelity:ops` writes none. What holds them to the console instead:

- **They are built out of the console's own parts.** Each is one queue on one panel, at `--ops-panel`, headed by its title and its count, with a row for each waiting thing and the decision on that row, as board C1's review queue and board D1's no-show queue are. Ink carries the one primary action; a rejection asks for its reason in board C1's own field; a row that has run over its time is marked in oxblood, as board D2 marks one.
- **Every word is a placeholder**, and marked as such in `apps/ops/src/content.ts`, since no board writes any of them.
- **One thing is drawn nowhere else: the deletion's confirmation.** It is board D3's revoke carried further, because an erasure cannot be undone. Deleting takes two deliberate steps; the second writes out what is destroyed and what is kept, in the words the client's own app uses ("Invoices kept eight years, by law"), and offers nothing until ops confirm they have checked the request on the client's own number, which is the runbook's first step. It is the only control on the console drawn in oxblood, and it takes focus as it opens so that it is read by ear as well as by eye.
